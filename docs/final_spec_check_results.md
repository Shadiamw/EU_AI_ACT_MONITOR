## FINDINGS

### F1 (E52): POST /v1/webhooks answers an unparseable body with 400 before authentication and role checks

- Spec text violated (Phase3_Implementation_Spec, shared rules, Role matrix): "Wrong role is 403 FORBIDDEN_ROLE; missing or unknown key is 401. Order of checks: 401, then 403, then body validation (400), then SYSTEM-key mismatch (403 SYSTEM_MISMATCH)." And it says "Every other endpoint accepts REVIEWER or VIEWER", which covers POST /v1/webhooks.
- Audit claims contradicted: §1 '4 Order of checks' MATCHES; §3 'auth.require(*roles) … A framework dependency on every endpoint' MATCHES.
- Observed: when the body is not valid JSON, every caller gets 400 MALFORMED_BODY: no key, a wrong key and the SYSTEM key alike. When the body is parseable JSON, the order is correct: no key gives 401, the SYSTEM key gives 403 and the VIEWER key gives 400. POST /v1/metrics keeps the correct order for the same body, and so do the disposition and report stubs.
- Minimal repro, against the running server:
  ```
  curl -s -w ' %{http_code}\n' -X POST http://127.0.0.1:8000/v1/webhooks -H 'Content-Type: application/json' -d '{bad'
  # -> {"error_code":"MALFORMED_BODY","message":"the request is malformed"} 400   (expected 401 MISSING_OR_INVALID_KEY)
  curl -s -w ' %{http_code}\n' -X POST http://127.0.0.1:8000/v1/webhooks -H 'Content-Type: application/json' -H "Authorization: Bearer $INGEST_KEY_SYS_42" -d '{bad'
  # -> 400 MALFORMED_BODY   (expected 403 FORBIDDEN_ROLE)
  ```
- Evidence: `probe/raw/p02b_webhook_order.txt`. The repro was re-run at the end of the session with the same result.
- Cause, from reading the code after the live run: `app/api/webhook_routes.py` declares `body: WebhookIn` as a handler parameter. FastAPI decodes the JSON body before it resolves the `require("REVIEWER","VIEWER")` dependency. The JSON decode error therefore becomes 400 through the validation handler before auth runs. `/v1/metrics` avoids this by parsing the body in a dependency that runs after `require`.

### F2 (E193): no JSON request log line for 2xx or 4xx requests

- Spec text violated (§1.8 Observability): "One JSON log line per request: ts, level, request_id, actor_id, method, path, status, duration_ms, plus event_id when relevant."
- Audit claim contradicted: §11 'Request log' FIXED BY PLAN ITEM P17 (proof `test_observability.py::test_one_json_log_line_per_request`).
- Observed: I ran 16 test-environment runs and 2 production runs, with thousands of requests, using the README's start command (`python -m uvicorn app.main:app`; the launcher calls `uvicorn.run("app.main:app")`). The web log held only uvicorn's plain access lines. JSON request lines appeared only for 500 responses (level ERROR). This held with LOG_LEVEL=DEBUG and with the default.
- Minimal repro:
  ```
  python -m uvicorn app.main:app --port 8000   # ENVIRONMENT=test, DATABASE_URL etc. set, LOG_LEVEL=DEBUG
  curl -s http://127.0.0.1:8000/v1/events -H "Authorization: Bearer $REVIEWER_KEY"   # 200
  curl -s http://127.0.0.1:8000/v1/events                                            # 401
  # web log shows only: INFO: 127.0.0.1:… "GET /v1/events HTTP/1.1" 200 OK / 401 Unauthorized ; no {"ts":…} line
  ```
- Evidence: `probe/logs/p05.web.log` and the other `*.web.log` files. `probe/logs/p10prod.web.log` holds the only JSON lines, which are 500s. The re-check at the end of the session is in `probe/logs/p14prod.web.log` (its last two lines).
- Cause, from code read afterwards: `app/observability.py` logs the line to logger `api.request` at INFO. `app/main.py` sets the level of the `api` logger but attaches no handler. Python's last-resort handler therefore prints only WARNING and above. The module docstring says "The web process's log handler is Part 4's". This is a possible mitigation: Part 4's Dockerfile or start command, which is not built yet, may configure a handler. As delivered and as the README says to run it, the requirement is not met. I did not read the proof test; a caplog-based test would pass without a handler.

### F3 (E194): counters are neither logged nor exposed

- Spec text violated (§1.8): "Log counters (or metrics): samples accepted, duplicates, breaches, series joins, 4xx by code."
- Audit claim contradicted: §11 'Counters' FIXED BY PLAN ITEM P17 (proof `test_observability.py::test_counters`).
- Observed: no web log in any run contains counter output, and no metrics endpoint exists (GET /metrics returns 404 NOT_FOUND).
- Minimal repro: send any number of samples to POST /v1/metrics, then grep the web log for a counter. There is none. `curl -s http://127.0.0.1:8000/metrics` returns 404.
- Code read afterwards: the counters live in memory only (`observability.counter_values()`). Nothing logs them or serves them.

### F4 (E195): LOG_LEVEL=DEBUG produces no threshold-evaluation debug lines

- Spec text violated (§1.8): "Log every threshold evaluation outcome at debug level with the version id, so a disputed flag can be reconstructed." Related: §5, "LOG_LEVEL | INFO".
- Audit claims contradicted: §11 'Threshold debug log' FIXED BY PLAN ITEM P17 (proof `test_observability.py::test_threshold_evaluation_debug_line`); §2 'LOG_LEVEL' FIXED BY PLAN ITEM P17.
- Observed: the web process ran with LOG_LEVEL=DEBUG in every run and evaluated about 700 samples. No evaluation line appeared.
- Minimal repro: start the web process with LOG_LEVEL=DEBUG, then POST the sample `{"system_id":"sys-42","metric_name":"accuracy_drift","metric_type":"drift","value":0.34,"timestamp":"2026-10-06T02:00:00Z"}` with the SYSTEM key. The response is 201 with flagged_event_id. The web log has no line naming thr-1.
- Evidence: `probe/logs/p04.web.log` and `probe/logs/p05.web.log`. The cause is the same as F2: the line goes to `api.detection` at DEBUG, and no handler is attached.
